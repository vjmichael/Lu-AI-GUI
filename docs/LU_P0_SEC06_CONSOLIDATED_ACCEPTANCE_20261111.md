## Purpose and strict evidence rule

An adversarial source assertion, SQLite simulation, compiler success,
positive return code, or completed model answer is not independent OS
custody evidence. A specific original worker / cgroup / Windows Job, source
head, original effect journal and owner-visible restart state must agree.
The test program never restores tool permission or retries effects.

Native receipts generated by `scripts/p0-sec06-consolidated.mjs` preserve
the test machine OS, exact HEAD, SHA-256 of the source inventory, individual
test names, result codes and SHA-256 hashes of each saved log. These local
hashes detect accidental or post-run evidence modification; they are **not**
remote signatures, trusted-machine attestations or proof against a same-user
attacker who can replace both the receipt and the logs. Independent review
and owner physical acceptance remain mandatory.

The independently verified kernel preflight states `ancestorCgroupProcsUserWritable=true`: the setsid descendant escaped into the same-UID writable service ancestor, the leaf became empty, and the custodian issued a false cleanup receipt. This is not a CI provisioning problem and cannot be accepted as containment. The original Linux receipt is `BLOCKED_NATIVE_SECURITY`; its 23 case-log SHA-256 values and its delegated-kernel witness digest have been independently verified.

**SEC-06C immediate source security repair:** reject a same-UID-owned or writable ancestor `cgroup.procs` before any worker admission or positive receipt; require nonroot account and an independently owned, non-writable nearest common ancestor. The guardian emits `UNSAFE_ANCESTOR` instead of `READY`, and the Rust host rejects `SEC06C_BLOCKED_UNSAFE_WRITABLE_ANCESTOR` rather than falling back to process-group containment. The guardian rechecks the boundary before generating the final historic receipt, with source regressions. This deliberately blocks the current simple `Delegate=yes` service: **source-level rejection does not establish secure worker execution**.

The architectural completion gate is a **trusted OS-managed/root-owned outer cgroup control boundary and brokered worker admission** (or equivalently independently enforced kernel isolation): the untrusted worker must not have write permission to the destination or common ancestor `cgroup.procs`, while the trusted broker—not same-UID worker code—must attach the first worker before executing untrusted code. A plain delegated service with a worker-owned ancestor cannot meet this criterion. Do not make its `cgroup.procs` writable again for test convenience, test it only with a positive kernel-backed hostile migration attempt, and keep SEC-06C/SEC-06F BLOCKED until a real passing original-run proof exists.
