# PERF-01 P6 — Local Multi-GPU and Optional Compute-Node Scheduling

**Date:** November 12, 2026. **Branch:** `lu/perf01-p6-multigpu-nodes-20261112` stacked on `lu/perf01-p5-inference-tuning-20261112`. **Status:** implementation in source; **real native and installed acceptance open**. No CI run, PR, merge or release.

## Goal, current installation and source of truth

Lu must remain a normal offline single-machine Tauri/React + GGUF local application on one GPU. It may use two local GPUs in either mode after hardware verification: **one model layer-split across two GPUs** or **two independent resident model instances** executing different explicitly admitted requests. An optional external compute node is not assumed to be installed, online, authenticated or available. Preserve Lu's original model/session custody, per-turn authority, ANSF+SQLite memory, cancellation, journal and host approval. Avoid mandatory Docker, MCP, remote nodes or automatic tensor splitting.

The installed Lu desktop **still constructs exactly one** `TrustedInferenceSupervisor<PersistentLlamaBackend>` with `tuning:None`. The new P6 local coordinator starts empty, with zero verified additional GPU devices, zero reservations and no remote node connections. The new Resource Guardian fields explicitly show that this is an unknown capacity, **not evidence that no physical second GPU exists**.

## Implemented host-native source

**1. Device evidence and capacity accounting.** `src-tauri/lu-core/src/p6_compute_fabric.rs` provides `LocalGpuCoordinator`, `GpuObservation`, `GpuRequest` and `ApprovedLocalGpuPlacement`. It requires a nonzero exact pinned engine SHA-256, exact allowlisted llama.cpp device names, native GPU-memory observation specifically marked as verified, a finite observation timestamp no more than five seconds old, nonnegative physical capacity and actual model-specific measured VRAM requirements. Each reservation adds 512 MiB safety margin per device, counts already reserved capacity and rejects unknown/stale/conflicting/oversubscribed requests. At most two local devices and two reservations are allowed. The source does **not** invent device memory from GGUF size, Vulkan presence, Linux `/dev/dri` files or CPU RAM.

**2. Local split-model placement.** Experimental, allowlisted `--device Vulkan0,Vulkan1 --split-mode layer --tensor-split 50,50` is constructed only for an exact two-device layer-split plan with positive fractions summing to 100. The device names and fractions must originate from a trusted native planning path, not model output. llama.cpp's newer `tensor` parallel mode and deprecated `row` mode are **not adopted**. Actual bundled-engine flag support and observed VRAM fit are unverified. The normal `--n-gpu-layers` selection from the previous P5 experimental profile still applies.

**3. Independent instance placement.** A separate plan uses `--device <exact-device> --split-mode none`. `reserve_best_independent` chooses a verified device with the largest remaining measured headroom; a second independent instance is admitted on the other device when the first cannot fit there. `LocalIndependentFleet` selects from distinct original, separately loaded `TrustedInferenceSupervisor` sessions, round-robin, by exact model identity. Both source paths require an original free/ready session; concurrent claims still pass the original supervisor's reservation. The fleet does **not** execute chat turns, write ANSF or confer tool authorization. It has no hidden effect retry or fallback after inference begins. Real dual-instance desktop wiring is intentionally held until native device evidence and custody tests pass.

**4. Lease and crash custody.** Approved GPU placements carry a weak reference to their exact original coordinator reservation, session ID, selected devices and pinned engine SHA. `PersistentLlamaBackend::new` checks the engine binding and `load_with_projector` checks again before process spawn. Releasing the reservation invalidates every copied placement. `release_verified` refuses wrong sessions and **never releases resources on uncertain child cleanup**. Existing supervised OS process / Job Object cancellation and ANSF incomplete-output recovery remain authoritative. Reappearing GPU names or old PIDs after restart are not proof an escaped process was reaped.

**5. Remote nodes are optional and explicitly disabled.** `OptionalComputeNodes` stores up to four operator-reviewed DNS identities, ports, pinned TLS certificate SHA-256, remote engine SHA-256 and model SHA-256. It rejects missing/malformed identity proofs, credentials embedded in URLs and duplicate registrations. `admit_remote_request` currently returns `RemoteTransportDisabled` **even for a registered identity**. There is no remote TCP connection, token forwarding, model-generated endpoint, automatic retry, remote tool use, shared filesystem assumption, silent source egress or remote cancellation claim. Secure mTLS streaming, host-scoped request/proposal policy, independent remote process custody, remote model verification, failure reconciliation and offline fallback are separately outstanding engineering tasks.

**6. Operator visibility.** The existing Resource Guardian displays the number of locally verified P6 devices, active additional reservations, reviewed remote candidates and `remote inference disabled` rather than implying two GPUs/remote nodes are present. This read-only view is scoped to the selected original chat and cannot authorize GPU leases or network connections.

**7. Performance comparison pipeline.** `scripts/perf01-p6-local-comparison.mjs` accepts only bounded original exact-head comparison receipts with pinned engine/model SHA-256, fixed hardware ID, exactly two observed local GPUs, and at least five matching trial IDs **in all three modes** (`single`, `layer_split`, `independent`). It reports TTFT p50/p95, total latency p50/p95 and basic exact-quality pass counts. It rejects stale source heads, duplicate/incomplete trials, invalid timing values and one-GPU receipts mislabeled as two-GPU comparisons. The output explicitly sets `physicalAcceptance:false`, `comparativeSpeedupAccepted:false`, `independentDeviceConcurrencyVerified:false`, `gpuVramAvailabilityIndependentlyVerified:false`. No fake p50/p95 values are included in this ledger.

### Actual tests and evidence this source turn

Added Rust unit tests: default zero-device/no-network; two-device layer split flag construction; two independent VRAM reservations; deterministic best-device selection and overcommit rejection; expired/missing/forged device proof; wrong-session and uncertain-child release refusal; revoked copied placement; duplicated physical supervisor denial; real original supervisor model/session selection with two fake engines; remote descriptor sanitization/no-egress. These **were authored, not executed**.

Added Node source-contract test `lu-desktop/tests/perf01-p6-compute-fabric.test.mjs`. Its five checks passed in an isolated JavaScript harness using current GitHub-fetched source. The comparison analyzer was parsed and exercised in isolation with **synthetic** data: five complete paired trials per mode summarized, while missing-trial, stale-SHA and invalid-time fixtures were refused. Native Rust/Cargo is not present in this working environment; no actual Windows/Linux build, pinned llama.cpp run, Radeon VRAM reading or installed UI was executed.

### Remaining implementation and acceptance gaps

1. **Trusted native GPU enumeration and memory probe (P6-GATE-1).** Windows DXGI/driver/backend and Linux backend-specific memory availability must be implemented and verified. Existing `platform_compute` only reports hints, and Windows currently reports the GPU probe adapter unavailable. No production `GpuObservation.native_memory_probe_verified=true` producer has been built. This is the primary blocker to enabling two local GPUs in the installed desktop.
2. **Real local fleet integration (P6-GATE-2).** Connect second `TrustedInferenceSupervisor` through the installed host's original model, generation queue, chat ID, ANSF checkpoint, authority, cancellation and warm-residency lifecycle. Validate exact engine identity/lease as native process starts, exact per-device VRAM and model MMProj behavior, plus process-tree cleanup and restart reconciliation. Preserve default one-GPU route; avoid creating phantom second backends.
3. **Native physical A/B benchmarks (P6-GATE-3).** Fixed model, engine commit SHA and prompts on genuine two-GPU hardware, with 5+ repeated alternating trials in single-GPU, layer-split and separate-instances modes. Collect real TTFT, prompt/decode throughput where available, VRAM/CPU/RAM peaks, simultaneous-session task throughput, power, quality, cancellation and failure recovery. Do not infer speedups from synthetic analyzer tests or mere launch-flag existence.
4. **Optional authenticated remote transport (P6-GATE-4).** Only after explicit owner opt-in: validated TLS identity (mTLS), node policy/manifest, model and backend version equality, streaming checksum and bounded buffering, cancellation propagation, no tool-authority transfer, recovery and audit receipts. If disconnected, do not silently retry potentially applied effects. Remote endpoints remain disabled until accepted.
5. **Consolidated exact-head native/security acceptance.** Build current stacked Lu head on Windows/Linux, repair all compiler errors, run P2/P4/P5/P6 regression, genuine GGUF + MMProj and native Job/cgroup tests, installed-human Radeon smoke and repeated GPU accounting. The existing P0/P4 deterministic CPU-first path and offline single-model flow must continue to pass.

### Notes about upstream llama.cpp

The public llama.cpp multi-GPU guide describes `--device`, `--split-mode none/layer/tensor`, `--tensor-split` and `--list-devices`, and cautions that tensor parallelism is experimental and backend-specific. It is not a compatibility guarantee for Lu's exact pinned package. See https://github.com/ggml-org/llama.cpp/blob/master/docs/multi-gpu.md .

**Disposition:** P6 source-level local strategy and conservative no-egress boundary implemented provisionally. **Do not mark full P6 operationally complete**: real device observation, installed second supervised GPU backend and remote transport remain open. Next independent PERF feature is P7, but P6 native integration/acceptance must stay in the backlog.
