# E1-P06E — reviewed native FFprobe WAV/MP4 inspection

## Purpose and architecture

Lu can ask a real, host-reviewed external FFprobe application to inspect a
local audio or video file: duration, codecs, sample rate and channels, and
frame width/height. This is the next useful application integration after
Git. The implementation is a native host-only broker; model-facing tool
registration and desktop UI are not yet included.

**Lu itself remains an unsandboxed native desktop application.** Windows Job
Objects and Linux process groups supervise *children* for cancellation and
recovery. They are not a mandatory sandbox on Lu Core.

## Exact host-selected admission

- Host enrolls the precise executable SHA-256 and app identity, the approved
  absolute local media path, file SHA-256, workspace, distinct read/execute
  tool identities, output ceiling and deadline.
- Only regular symlink-free/reparse-free local inputs 1 byte to 256 MiB,
  with no dot or parent traversal components, are admitted.
- Container is explicitly host-reviewed WAV or MP4. The fixed application
  command forces the WAV or MOV demuxer; it does not auto-detect playlists.
- FFprobe receives these exact argument elements:
  -v error; -protocol_whitelist file; -f wav or mov;
  -show_entries format=duration:stream=index,codec_type,codec_name,width,height,sample_rate,channels;
  -of json; -i [host-approved absolute path].
  No model-supplied process path or generic argv is admitted.
- File SHA is checked at enrollment, current-turn preflight, OS supervisor
  admission immediately before launching, and again before committing a
  semantic journal result.
- The original authenticated human turn must grant ReadWorkspace for
  the selected media and ExecuteCode for the reviewed FFprobe action. Both
  grants are separately reviewed by host policy. Neither model text nor
  app discovery confers authority.
- Child uses cleared environment, null stdin/stderr, host-only stdout
  bounded to 16 KiB, and 1–30 second deadline. The process is OS-reaped by
  Lu supervisor before output is accepted.

## Untrusted JSON parser and journal

Only a finite, strictly typed JSON object is accepted: a numeric finite
duration (1 ms to seven days), at most sixteen audio/video streams with
unique bounded IDs, known safe codec names, video width/height or audio
sampling rate/channels. Unknown or nonempty metadata sections, paths,
tags, invalid numbers and unexpected stream fields are rejected.

A successful external process exit is not evidence of correctness by
itself: the broker also requires strict parsing, OS reaping and the
same approved media digest. SQLite records only normalized media facts,
output SHA/length, reviewed input digest and custody/authority status.
Raw media bytes, raw JSON, filenames and paths are not journaled.

Failed spawn, cancellation, revoked grant, timeout, bad/malformed stdout,
invalid media and modified inputs cannot become APPLIED. These cases
remain UNCERTAIN and cannot replay an ambiguous action automatically.

## Windows/Linux native verification

The dedicated lu-e1-p06e-ffprobe.yml workflow asserts the exact PR branch
head and frozen source inventory, then selects genuine installed FFprobe and
FFmpeg binaries on Windows 2025 and Ubuntu 24.04, recording their hashes.
Each platform must execute five actual native tests, not just compile:

1. Genuine one-second mono PCM WAV: 1000 ms, pcm_s16le, 8000 Hz, one channel,
   successful reaping and SQLite persistence, independent host veto denied.
2. Genuine MPEG-4 MP4 generated by real FFmpeg: 1000 ms, mpeg4, 32x32 pixels.
3. No read grant, forged assistant-origin user turn, wrong workspace and
   injected command payload must all be denied before execution.
4. A host-approved but malformed media file must fail FFprobe and remain
   journal UNCERTAIN with no applied receipt.
5. Modified file after host review must fail before effect preparation.

Separate parser and file-hash rejection tests also run. Native acceptance
remains OPEN until both platforms report five genuine process tests passed,
their complete logs and exact source identities. Missing installed FFmpeg
or FFprobe on a runner is a dependency blocker, not a passing test.
Independent local FFprobe checks already observed valid WAV and MP4 JSON;
they do not prove Lu's native Rust execution.

## Boundaries and later work

This is not a generic command runner, an FFmpeg editing tool, automatic
whole-disk media discovery or a model-selected file path. It is not yet
registered as a model-visible desktop tool. Filesystem stat/canonical checks
and SHA before/after do not eliminate all TOCTOU conditions; stronger
handle-pinned path custody is a future high-risk input boundary. Forced
container type and local-file-only protocol minimize playlist-like hazards,
but do not prove full OS/network isolation of FFmpeg internals.
The existing P03/P04B/P05/P06B/C/D real native and model benchmark gates
remain independent OPEN items.
