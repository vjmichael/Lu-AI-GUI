# TOOLS-04 — Native archive inspection (Jan-first design review)

**Decision:** 2026-11-04. **Scope:** Basic *read-only ZIP metadata listing* in Lu Core.  
**Source authority:** [Original Jan-Mod Design](reference/Jan-Mod-Design-Document.md) and [merged Lu Native Tools Design](LU_NATIVE_TOOLS_MERGED_DESIGN.md). This is an implementation record, not a competing design.

## Original design versus later explicit Lu goal

- The original `Jan-Mod-Design-Document.md` §5.2 prescribes consolidated **internal** file/read/search native domains with **small model-facing task-specific schemas**, typed Protobuf (§4.6), host action gating (§3.7), a reliable boundary (§4.8), durable effect journal (§4.9), and loop guard (§7). **It does not specify a separate archive/ZIP tool, archive extraction API, or archive creation API.** Do not invent claims of original archive-specific instructions.
- Explicit later Lu core scope in `LU_CENTRAL_DESIGN.md` §3.3 and `LU_V1_0_TASKS.md` TOOLS-04 authorizes archive/compression as **basic first-party Core capability**.
- Implement this as a **file/read-domain adjacent native archive service**, `lu.archive`, with **one narrow optional model facade** `lu_archive_list(path,max_entries?)` exposed *only* to an authenticated per-turn workspace/file inspection grant. No user JSON file inspector or archive GUI required.
- This avoids the JSON tool mistake: ZIP listing is an actual user-delegated file action (read-only), while JSON MBRL is an **internal boundary**. ZIP creation/extraction, change of permissions, symlinks, remote fetches and installer provisioning require distinct designs/grants.

## Exact first-stage contract

| Boundary | Implementation |
| --- | --- |
| Model-visible JSON | `lu_archive_list(path,max_entries?)` with small exact schema; no arbitrary archive command/extract destination |
| Typed native Protobuf | `ArchiveListRequest`, `ArchiveEntry`, `ArchiveListResult`; type-URL match and strict/re-encode canonical check |
| Trusted root | Host-owned directory capability (`cap-std::fs::Dir`); model can supply **only** lexical workspace-relative `.zip` file path |
| Human authority | `ReadWorkspace` effect, task-authorized `NativeToolTurn`, host authorizer recheck at dispatch; no discovery-as-grant |
| Parser | Maintained `zip` Rust crate pinned to `9.3.0`, metadata-only `ZipArchive::by_index_raw`; **never** call `extract`, `by_index` or decompress member content |
| Validation | Reject absolute/traversal/ambiguous path, control chars, backslash, duplicate normalized entry names, symlinks and unsupported special file kinds |
| Resource budgets | ZIP source max 32 MiB, hard count 4096 entries, return max 256, per-file declared uncompressed <=64 MiB, aggregate declared <=256 MiB, expansion ratio <=1000 |
| Results | Entry names, kinds, compressed and *declared* uncompressed sizes, declared CRCs, limited entry count and truncation status; **no CRC verification or content-safety claim** |
| Failure | Host-defined typed, nonretryable errors, no extracted files, no execution, no unsupported format guess |
| Platform | Linux/Windows real ZIP tests, malicious path/duplicate, size boundary, Protobuf and denied/revoked task |

The [RUSTSEC-2026-0429](https://rustsec.org/advisories/RUSTSEC-2026-0429.html) advisory affects older `ZipArchive::extract` versions and illustrates why the Core listing must be non-extracting and use a patched library, not write a homegrown ZIP parser. Even a clean manifest is **not proof** that a later extraction would be safe.

## Unfinished acceptance

- Cargo lockfile must be generated by Cargo (not guessed) in **both** `src-tauri/lu-core/Cargo.lock` and `lu-desktop/src-tauri/Cargo.lock`, with exact source lock refreshed. Initial development CI can report the Cargo-resolved delta; final CI must return to `--locked`.
- Real ZIP fixtures include duplicate paths, traversal/backslash, over-budget declarations and symlinks; the hardened ZIP writer/reader and Rust type interfaces must compile on both OSes.
- Actual desktop model/tool orchestration and target-level human approval are still open cross-tool v1.0 acceptance gates; no `lu_archive_list` UI is declared shipped merely because this Core library passes CI.
- For future **creation/extraction**: separate file-effect grants, path/custody validation on every member, atomic destination publication, resource/ratio caps based on actual decompression, archive recursion rules, safe ownership/permissions, durable journal and crash/cancel/recovery. Do **not** reuse this metadata-only manifest as an extraction certificate.
- No TAR/7z support is claimed until an established library, format-specific security plan and tests are added. No `unzip`, PowerShell, shell or non-native CLI installed here.
