# IDE-CORE-IPC-01B-R3 — native approval and Core issuer interoperability handoff

**Status (2026-11-21):** IDE-only native client + disposable installed-path Linux UI acceptance. No production issuer or signed release. Exact original IDE PR #236 base `f1f0ed4bc1e740d2a9f85615b988b779a46651db`, with unpublished R2 and R3 local patches. **Lu Core source is not modified.** Core-owner blocker: https://github.com/vjmichael/Lu-AI-GUI/issues/245.

## Native UI contract

- Compile-time opt-in `native-core-health`; default release and Windows still have no Health control. At Tauri `.setup` the *fixed* root-owned `/etc/lu-ide/native-health-v1.json` must admit the real OS UID, exact executable path + measured SHA-256, issuer UID/GID, installation package commitment and private journal. Invalid/missing profile leaves the IDE usable **without** a Health menu.
- The admitted process attaches a **native menu** with `Check Lu Core health…` and `Cancel Core health check`. A native menu event alone does **not** borrow an enrollment. It claims exactly one non-cloneable permit per process, then a separate OS-native approval dialog requests one read-only Health observation. Declining consumes and fsyncs a `cancelled` journal marker without connecting to the issuer. Revocation consumes the permit; an abandoned dialog cannot be retried by the same process. Late completion is refused after cancellation/revocation. Results are fixed strings; no key, socket, operation ID or health detail enters the WebView or model.
- The popup is a **human-facing confirmation**, not signed proof of physical human presence. X11 event injection can click it; a real installed issuer MUST independently authenticate the requesting OS process, installed publisher/package and one-use entitlement, and must not rely on the UI's yes/no bit as a Core grant. No WebView `invoke` handler for the Health action is registered.
- On explicit acceptance, the IDE journal writes one reserved and one started marker before issuer contact. Failures are terminal `refused` or `uncertain`; no automatic replay. A Health success gives read-only advisory information, **never** model/tool execution.

## Independent installed issuer requirements (Core/OS owner)

- A privileged separately owned **Linux UDS** issuer must be installed and supervised. The IDE currently pins an absolute UDS path, exact issuer UID, access group and kernel `SO_PEERCRED`; root/service-owned 0750 parent + 0660 socket. Windows SCM/named-pipe signed publisher admission is *not yet implemented* in this IDE track and remains default-deny.
- The native issuer's input is `lu.ide.v1.NativeHealthLeaseRequest` from `ide/proto/lu/ide/v1/native_broker.proto`. Require canonical frame (`u32` big-endian length, 1–4096 bytes), schema 1, 32-byte fresh nonce, one original 32-char lowercase hex durable journal operation ref, 32-byte pinned package SHA, and **exact scope** `core.health.readonly`. Verify the original OS caller PID+UID, independently measured signed installed executable and issuer-local enrollment authorization. A user-supplied package digest alone is not attestation.
- **Burn** each operation reference durably and atomically in issuer-owned storage *before* returning any credential. A restart, duplicate, race, downgrade, revoked enrollment or foreign operation must not acquire a second lease. The issuer must be able to reject after revocation and independently enforce TTL.
- Reply `lu.ide.v1.NativeHealthLeaseReply` must echo schema, nonce, package digest, scope and operation ref exactly, and provide an absolute canonical Core UDS path, pinned Core owner UID, **one** fresh 32-byte ephemeral HMAC enrollment and an expiry within 60 seconds. No credential goes to files, logs, model or WebView. The IDE immediately zeroizes its transient key after the single callback.
- The actual **Core-owned** `lu.workspace.v0` endpoint must authenticate Linux OS peer + HMAC Hello/Challenge/Proof/Welcome, then serve **only** `HealthRequest -> HealthReport` initially (module ID `lu.core`, nonzero epoch); it must not infer `READ_WORKSPACE`, tool, model, file or execution capabilities. Core health dispatcher and enrollment remain pending in Core issue #245.
- Independent interoperability run MUST use two separately installed OS processes with accepted service/package identity and a real Core health epoch. Required negatives: wrong signer/UID/nonce/package/ref, stale and reused lease, Core socket swap, cancelled/revoked operation, peer restart, crash after reserved/started, tampered journal, truncated/oversized frames, and no autoconnect on IDE startup. All OS evidence and accepted Core source SHA must be recorded. **Synthetic fixtures do not satisfy this gate.**

## Executed R3 Debian acceptance (not a production signed release)

- Shared Debian13 GUI dependencies verified by 438 SHA-256 package checks and staged privately; exact Rust 1.99.1 Cargo and frontend locked npm cache; Tauri feature `native-core-health` checked and executable linked with locked offline Rust dependencies.
- Disposable root-owned `/opt/lu-ide-r3/bin/lu-ide-desktop` with an OS-administered *test* profile and journal, run as actual UID/GID 65534 under Xvfb/DBus. Profile absent: IDE window opens but Health admission refused. Profile present: native menu appears and opens native confirmation; **no issuer or Health request merely from startup**.
- Actual native click **Deny / Cancel**: durable `reserved + final(cancelled)` (no `started`, no issuer connection); repeated click does not create another operation. After restart, actual **Approve one health check** with no issuer: `reserved + started + final(refused)`; native result redacted, no auto retry. Profile executable SHA tampered: startup refused while IDE window still opens, existing journal unchanged. These test fixtures do not independently verify signed publisher custody or a real Core Health reply.
